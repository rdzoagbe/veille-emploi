# Veille Emploi recovery and operations runbook
## Backup scope and limitations
The production application uses the public schema and custom sessions. On 26 Nov 2026 the live inventory was 1 real account, 46 offers, 2 sessions, zero managed Auth accounts and zero Storage objects. Inventory changes over time. Supabase Free does not provide automatic managed database backups. The repository is not a backup of live records.
Use `scripts/backup-public.ps1` on a trusted Windows computer (PowerShell 7, PostgreSQL client compatible with the server and age). Configure the database connection using local PGHOST/PGPORT/PGDATABASE/PGUSER, PGSSLMODE=verify-full and a protected PGPASSFILE; use the dashboard's direct or session-mode connection. Do not paste passwords into chat, commit them, or expose them on a command line.
Generate an age identity locally (`age-keygen -o identity.txt`), keep the private identity outside synced folders, and use only its public age recipient for scheduled backups. Run the script with -Recipient and -Destination pointing to a local encrypted-archive folder or a private Google Drive-synced folder. It streams pg_dump directly into encryption and writes a SHA-256 sidecar. Protect the DB credential with local filesystem permissions. Use Windows Task Scheduler under that same user account daily; monitor failed runs and retention (e.g. 14 daily and 4 weekly archives). Never silently delete the last verified archive.
The archive contains the public schema and records, including sensitive subscription and session metadata. It does not contain Edge Function secrets, Gmail passwords, Vault/cron configuration, managed Auth or Storage objects. Maintain separate encrypted recovery records for configuration, and re-evaluate managed Auth and Storage when used. No plaintext backups, credentials or real account records belong in GitHub.
## Restore drill (isolated environment only)
1. Verify the encrypted archive checksum against its sidecar. Decrypt using age and the offline identity into a protected temporary location on a trusted machine; verify `pg_restore --list` and inspect its contents. Delete the plaintext after the drill.
2. Restore into an isolated compatible Postgres/Supabase staging database, not the live project. Review role grants, policies, functions, sequences, triggers, foreign keys and record counts. Never blindly restore over production.
3. Prevent live mail delivery, disable cron, and rotate/revoke restored sessions, verification codes and unsubscribe tokens as appropriate before any public access. Recreate secrets and cron only when verified and intended. Run the app's synthetic account isolation checks and compare record counts. Test that encrypted archive can be decrypted by the offline key.
4. Record date, backup hash, restoration outcome, any missing objects, and measured recovery time. Until a successful restore drill, recovery is not verified.
## Operations
Check cron job `veille-alerts` and recent cron.job_run_details. A succeeded cron run / HTTP 202 only means the work was accepted; inspect function completion logs and send_log separately. Alert errors and source errors require review; forward send_log.error currently stores result codes (ok/upd/dup), not necessarily failures. Track aggregate errors without recording email content or addresses.
Keep free-tier quotas under review; 120 verification emails/day and 30/hour are current service limits. Add abuse protections before public promotion. No new paid services required.
## Security baseline
RLS enabled on 11 public tables. Core application records and sessions are service-role-only; existing legacy profiles/alerts policies are distinct and should be reviewed before removing their grants. The diagnostic function is a 404 stub. pg_net extension-in-public advisory is outstanding; do not relocate it casually because it supports the scheduled HTTP job.
A live synthetic two-account test on 26 Nov 2026 verified own-history reads, cross-account status rejection, no cross-account deletion and unauthenticated rejection. Test accounts were removed; 46 real offers preserved. v0.13.2 corrects misleading success responses for nonexistent/unauthorized deletions. Tests on mocked browser sessions are not a substitute for a real recovery drill.
